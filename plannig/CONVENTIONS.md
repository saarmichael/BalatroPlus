# Balatro+ Conventions

How Balatro+ code, data and tests are organised. Read this together with `BALATRO_PLUS_AGENT_BRIEF.md`.

API facts below were checked against the Steamodded sources: the smods repo at commit `733046a` (2026-10-06) and the docs repo `Steamodded/wiki` at `a6b1efa`. The GitHub wiki now redirects to docs.smods.dev.

> **Version note.** Steamodded now uses date-based versions (latest release `26.1002.0`). Our manifest requires `>=1.0.0~BETA-1814a`, and that string is still satisfied, because the version parser compares the major number first. Some APIs below only exist in newer builds. They are marked **(26.x)**. Before the pilot, check the installed smods version and raise the dependency if we rely on a 26.x feature.

## 1. Where things live

The brief's layout, mapped onto this repo:

| Brief path | Repo path | Notes |
|---|---|---|
| `design/jokers.csv` | `plannig/design/jokers.csv` | Master design table. Generated by `tools/extract_vanilla_jokers.py`, then edited by hand (design columns only). |
| `specs/jokers/<vanilla_key>.yaml` | `plannig/specs/jokers/<vanilla_key>.yaml` | One ticket per approved row |
| `src/jokers/<plus_key>.lua` | `mod/src/jokers/<plus_key>.lua` | One file per "+" joker |
| `src/upgrade_map.lua` | (none) | Built at load time from `BPlus.Joker` calls (`BPlus.upgrade_map`) |
| (mechanics) | `mod/src/mechanics/<id>_<name>.lua` | One file per mechanic M1-M10; numbers in `mod/src/balance.lua` |
| `assets/` | `mod/assets/1x`, `mod/assets/2x` | smods requires this layout |
| (tests) | `mod/dev/tests/jokers/<vanilla_key>.lua` | Automated acceptance tests, see section 9 and `docs/testing.md` |
| `tools/` | `tools/` | Dev scripts. Never inside `mod/`, because Steamodded treats any `.json` in a mod folder as a manifest. |
| `CONVENTIONS.md` | `plannig/CONVENTIONS.md` | this file |

**Game source is never committed.** The vanilla source (Balatro `1.0.1o`) is copied to `~/Documents/Code/Personal/balatro-vanilla-src/Balatro.love/` (outside the repo) and only read from there.

## 2. Mod header

`mod/BalatroPlus.json` is the Steamodded manifest.
- **Required fields:** `id`, `name`, `author` (array), `description`, `prefix`, `main_file`.
- **Our values:** prefix `bplus`, main file `main.lua`.
- **Defaults:** read from `mod/config.lua` (`return { ... }`) via `BPlus.config`. User changes are saved to `config/BalatroPlus.jkr`.

`main.lua` stays a thin loader. Load files with `BPlus.load('src/...')`, which wraps `SMODS.load_file`.

**Load order** (`main.lua`):
1. `src/core.lua` (helpers: `BPlus.dict`, dotted paths, `BPlus.load_dir`)
2. `src/balance.lua` (every mechanic number, as `BPlus.balance`)
3. `src/upgrade.lua` (`BPlus.Joker`, the upgrade map, `BPlus.upgrade_card`)
4. `src/behavior.lua` (behaviour switching for Carpenter / The Rust, section 6)
5. every file in `src/jokers/`, then every file in `src/mechanics/` (name order)
6. dev toolkit

In dev mode `BPlus.load_dir` skips a file that errors while loading, logs it, and the test runner prints it as
`WARN  mod file skipped at load: ...`. So one broken joker file never takes the other tests down. If your
joker's tests say its key is unknown, look for that WARN line first.

## 3. Keys and names

| Thing | Rule | Example |
|---|---|---|
| Vanilla key | Exactly as in `game.lua` `P_CENTERS` | `j_ride_the_bus` |
| `SMODS.Joker{ key = ... }` | Vanilla key without `j_`, plus `_plus` | `key = 'ride_the_bus_plus'` |
| Final plus key | smods adds the mod prefix, then the class prefix | `j_bplus_ride_the_bus_plus` |
| Joker file | `mod/src/jokers/<final plus key>.lua` | `mod/src/jokers/j_bplus_ride_the_bus_plus.lua` |
| Spec file | `plannig/specs/jokers/<vanilla_key>.yaml` | `plannig/specs/jokers/j_ride_the_bus.yaml` |
| Dictionary strings | `k_bplus_<name>` | `k_bplus_upgraded` |

How smods builds the final key (`SMODS.modify_key`): it adds the mod prefix only if the key doesn't already start with `bplus_`, then adds the class prefix `j_`. **Never write the prefixes yourself** in `SMODS.Joker{key=...}`.

Always reference other cards by their full key (`G.P_CENTERS.j_bplus_ride_the_bus_plus`).

## 4. Declaring a "+" joker

One file per joker. It must be self-contained: the joker, its text, and its state-transfer declaration.

Declare it with **`BPlus.Joker{...}`**, a thin wrapper around `SMODS.Joker` (`mod/src/upgrade.lua`). It registers the
`vanilla_key -> plus_key` map entry and fills in defaults: `rarity` and `cost` from the vanilla joker, placeholder
art, `unlocked = true`, `discovered = false`, and `in_pool` returning false. Reference implementations:
`mod/src/jokers/j_bplus_joker_plus.lua` (flat), `..._ride_the_bus_plus.lua` (scaling + state transfer),
`..._golden_plus.lua` (economy), `..._juggler_plus.lua` (add/remove_from_deck).

```lua
-- mod/src/jokers/j_bplus_ride_the_bus_plus.lua
-- Spec: plannig/specs/jokers/j_ride_the_bus.yaml
BPlus.Joker({
    key = 'ride_the_bus_plus',
    loc_txt = {
        name = 'Express Bus',
        text = {
            'This Joker gains {C:mult}+#1#{} Mult',
            'per {C:attention}consecutive{} hand',
            'played without a',
            'scoring {C:attention}face{} card',
            '{C:inactive}(Currently {C:mult}+#2#{C:inactive} Mult)',
        },
    },
    config = { extra = { mult_gain = 2, mult = 0 } },   -- ALL custom state in extra
    blueprint_compat = true, eternal_compat = true, perishable_compat = false,  -- always set all three
    bplus = { vanilla_key = 'j_ride_the_bus', state_transfer = { ['mult'] = 'extra.mult' }, carpenter_compat = true },

    loc_vars = function(self, info_queue, card)
        return { vars = { card.ability.extra.mult_gain, card.ability.extra.mult } }
    end,

    calculate = function(self, card, context)
        if context.before and not context.blueprint then
            -- face check -> SMODS.reset_card, else SMODS.scale_card (see the real file)
        end
        if context.joker_main and card.ability.extra.mult > 0 then
            return { mult = card.ability.extra.mult }
        end
    end,
})
```

**Rules**

- **State.** Put all custom numbers and state in `config.extra` and read them from `card.ability.extra`.
  - smods copies `config` into `card.ability`. But fields such as `ability.mult` and `x_mult` already have vanilla meanings, and `extra` is the only field that is reset when a card changes center (see section 6).
- **Numbers.** Every number in `plus_config` goes in `config.extra`. Never hard-code one inside `calculate` or `loc_vars`.
- **Text.** Use `loc_txt` in the joker file so that each ticket stays one file.
  - Formatting codes: `{C:mult}`, `{C:chips}`, `{C:money}`, `{C:attention}`, `{C:green}`, `{C:inactive}`, `{X:mult,C:white}` for ×Mult, `{}` to reset.
  - `#n#` is `vars[n]` from `loc_vars`.
  - Match the vanilla text style of the base joker.
- **Cost.** Always the vanilla joker's cost (`plus_cost = vanilla_cost`). Prices never change on upgrade.
- **Rarity.** Always the vanilla joker's rarity (`plus_rarity = vanilla_rarity`). Either `1`–`4` or `'Common'`/`'Uncommon'`/`'Rare'`/`'Legendary'` works; use numbers for consistency.
- **Tooltips.** To show the base joker, add `info_queue[#info_queue+1] = G.P_CENTERS.<vanilla_key>` in `loc_vars`.
- **Shop pool.** "+" jokers never spawn on their own: `BPlus.Joker` sets `in_pool` to return false. They appear only
  through the upgrade mechanics (Salesman, Craftsmanship/Masterwork, Masterwork Tag, Workshop Pack upgrade a vanilla
  joker the shop or pack already rolled). Don't override `in_pool` in a joker file.
- **Vanilla effects outside `calculate`.** Some vanilla jokers work through checks elsewhere in the game
  (`find_joker('Showman')`, `next(SMODS.find_card('j_ring_master'))`, `self.ability.name == ...` in game code).
  When the "+" version must keep or extend such an effect, hook the game function in the joker's own file, and
  detect the joker with `BPlus.find_behaving('j_bplus_..._plus')`, not `SMODS.find_card`, so that a vanilla joker
  next to Carpenter counts too and a "+" joker under The Rust doesn't.

## 5. `calculate` contexts

Signature: `calculate(self, card, context)`. Return a table, or nothing.

| Need | Context check |
|---|---|
| Main joker scoring | `context.joker_main` |
| Per scored playing card | `context.individual and context.cardarea == G.play` (card in `context.other_card`) |
| Held-in-hand effects | `context.individual and context.cardarea == G.hand and not context.end_of_round` |
| Retriggers | `context.repetition and context.cardarea == G.play`, return `{ repetitions = n }` |
| Before / after scoring | `context.before` / `context.after` |
| Once per round, end of round | `context.end_of_round and context.main_eval` |
| Blind selected | `context.setting_blind` |
| Discards | `context.pre_discard` (whole hand) / `context.discard` (per card, `context.other_card`) |
| Shop | `context.buying_card`, `context.selling_card`, `context.selling_self`, `context.reroll_shop`, `context.starting_shop`, `context.ending_shop`, `context.open_booster` |
| Consumables | `context.using_consumeable` (`context.consumeable`) |
| Other | `context.skip_blind`, `context.playing_card_added`, `context.first_hand_drawn`, `context.destroy_card` (return `remove = true`), `context.remove_playing_cards` |

**Return keys:**
- Scoring: `chips`, `mult`, `xmult`, `x_chips`, `dollars`.
- Other: `message`, `colour`, `card`, `message_card`, `func`, `extra` (a chained second effect), `remove`, `repetitions`, `saved`.

smods shows the default message for scoring keys, so don't add your own `message` for plain `chips`/`mult`/`xmult`.

**Blueprint / Brainstorm.**
- When a copy is evaluating, `context.blueprint` is set.
- Guard every **state change** (scaling, resets, self-destruct) with `not context.blueprint`.
- Return scoring effects normally.
- Set `blueprint_compat = false` only when the row says so.

**Scaling.**
- Use `SMODS.scale_card(card, { ref_table = card.ability.extra, ref_value = 'mult', scalar_value = 'mult_gain' })`. It handles the message and lets other mods hook scaling.
- Use `SMODS.reset_card` for resets **(26.x)**.
- Confirm in the pilot that the installed smods has `scale_card`. If not, scale by hand and show the message with `card_eval_status_text` / a `message` return.

**Probability. Always use the smods helpers**, so Oops! All 6s and other modifiers work:
```lua
-- loc_vars
local num, den = SMODS.get_probability_vars(card, 1, card.ability.extra.odds, 'bplus_<name>')
-- calculate
if SMODS.pseudorandom_probability(card, 'bplus_<name>', 1, card.ability.extra.odds) then ... end
```
- The seed string is always `bplus_<name>`, so it never collides with vanilla seeds.
- Never read `G.GAME.probabilities.normal` directly.

**Economy.** For end-of-round cash-out money, use `calc_dollar_bonus(self, card)` and return a number. Return `{ dollars = n }` for money given during play.

**Help while debugging.** `SMODS.debug_calculation()` records every context into `G.contexts`.

## 6. Upgrades and state transfer

The upgrade mechanics are designed in the brief ("Upgrade mechanics", M1–M10). Every permanent upgrade goes through **one shared helper**:

```lua
-- mod/src/upgrade.lua
BPlus.upgrade_card(card)   -- returns true if upgraded
```

**What it does:**
1. Look up `BPlus.upgrade_map[card.config.center.key]`. If there is no entry, return false.
2. Snapshot the source fields named in the plus joker's `bplus.state_transfer` from `card.ability`.
3. Call `card:set_ability(G.P_CENTERS[plus_key])`. In smods this transforms the card in place. Specifically, it:
   - calls `remove_from_deck` on the old center and `add_to_deck` on the new one,
   - fires `context.setting_ability`,
   - replaces `ability.extra` with the new center's config,
   - keeps every other `ability` field, including the `eternal` / `perishable` / `perish_tally` / `rental` stickers and `extra_value`,
   - keeps the edition, which is stored on `card.edition`, not in `ability`.
4. Write the snapshotted values to their destination paths.
5. Re-assert the edition and stickers from the snapshot. This guards against smods changing behaviour. Use `card:add_sticker(key, true)`; the `true` is required because vanilla stickers have `should_apply = false`.
6. Juice the card and show the `k_bplus_upgraded` message.

**`state_transfer` format** (both the CSV and the `bplus` table on the joker):
- A list of paths relative to `card.ability`.
- `"mult"` means copy `ability.mult` to the same path.
- `"mult -> extra.mult"` means copy `ability.mult` into `ability.extra.mult`. It is needed whenever vanilla kept state outside `extra`, which many vanilla jokers do (check `vanilla_config` and the source).
- Use `[]` when there is no persistent state.
- In Lua the declaration is a map: `state_transfer = { ['mult'] = 'extra.mult' }`.

**What to transfer** (decided, see "Scaling and decaying state" in the brief):
- **Growing jokers:** copy the built-up value (`"x_mult -> extra.Xmult"`, `"mult -> extra.mult"`, `"extra.chips"`, ...). The "+" growth rate applies from then on.
- **Shrinking jokers:** `[]`. The "+" joker starts from its own starting values.
- **Counters toward a step** (Yorick): copy the counter as is. The "+" joker normalises it to its own period in its own logic, `((remaining - 1) % period) + 1`, so the upgrade itself stays a plain path copy.

**Behaviour switching (Carpenter, The Rust).** Built once, in `mod/src/behavior.lua`; joker files contain no
Carpenter/Rust code. The brief's `base_calculate` / `plus_calculate` are generic:

- `BPlus.plus_calculate(card, context)` runs the "+" joker's code on any card; `BPlus.base_calculate(card, context)`
  runs the vanilla code on any card.
- They work by `BPlus.with_center(card, center, fn)`: for the duration of the call the card's `ability` and
  `config.center` are swapped for the other center's shape (a "view" built from that center's config, kept in
  `ability.bplus_alt`). The other center's own code then runs unchanged on the real card, so position checks
  (`G.jokers.cards[i] == card`), messages and juice all work.
- **The `state_transfer` paths are the fields both shapes share.** They are copied into the view before the call and
  back after it. That is what makes a growing joker keep its stored value while only the rate changes. So
  `state_transfer` must list *every* piece of state the two versions share (accumulated values, counters, the
  chosen card/suit/hand for the round when both versions use the same one). It is used for both permanent upgrades
  and temporary switching.
- Mechanics register a provider: `BPlus.add_behavior_provider(priority, fn)`, `fn(card) -> 'plus' | 'base' | nil`.
  Every hooked card function (`calculate_joker`, `calculate_dollar_bonus`, `add_to_deck`, `remove_from_deck`,
  `generate_UIBox_ability_table`) then follows the card's current behaviour. On a switch, deck effects (hand size,
  discards...) are removed under the old behaviour and re-added under the new one, like a debuff.
- `bplus.carpenter_compat = false` (shrinking jokers, Egg, Seltzer) makes the joker ignore every provider.
- Tests force a behaviour with `T.force_behavior(joker, 'plus' | 'base' | nil)`; it beats every mechanic. **Every joker
  with `carpenter_compat = true` gets one test of the vanilla joker forced to `'plus'`, and for growing jokers one of
  the "+" joker forced to `'base'`** (stored value kept, rate changes).

**Rules:**
- **No per-joker upgrade code.** If a joker needs more than a path copy, the row is not ready: send it back to `draft`.
- **The map is built at load time** from the `BPlus.Joker` calls (`BPlus.upgrade_map`, `BPlus.base_map`). There is no
  map file to edit: adding a joker means adding one file to `mod/src/jokers/`. (Changed 2026-10-07 so parallel
  work never edits a shared file; see `plannig/DECISIONS.md`.)

## 7. Art

- **Atlases:**
  - `SMODS.Atlas{ key = 'jokers', path = 'jokers.png', px = 71, py = 95 }` for final art.
  - `SMODS.Atlas{ key = 'placeholder', path = 'placeholder.png', px = 71, py = 95 }` for placeholders.
- **Image files:** go in `mod/assets/1x/` and `mod/assets/2x/` (2x is double size).
  - Newer smods **(26.x)** generates the missing size.
  - Ship both sizes anyway until we raise the dependency.
- **Atlas keys:** set as `atlas = 'jokers'`. smods prefixes them to `bplus_jokers`.
- **Grid order:** `jokers.png` is a grid in the same order as `vanilla_order` in the CSV. A plus joker's `pos` is its slot in that grid. Record the slot in the spec once art is final.
- **Placeholders:**
  - `placeholder.png` is one generic "+" card. Every joker with `art_status: none` or `placeholder` uses `atlas = 'placeholder', pos = {x=0,y=0}`.
  - Don't reuse the vanilla sprite, because players couldn't tell the two jokers apart.

## 8. Design table (`plannig/design/jokers.csv`)

- **Columns:** the brief's schema, plus extra vanilla reference columns produced by the extractor: `vanilla_order`, `vanilla_cost`, `vanilla_blueprint_compat`, `vanilla_eternal_compat`, `vanilla_perishable_compat`, `vanilla_effect_raw`, `vanilla_loc_vars`.
  - The unprefixed `blueprint_compat` / `eternal_compat` / `perishable_compat` columns describe the **plus** joker.
- **JSON cells:** configs, `state_transfer` and `acceptance_tests` are JSON in the cell.
- **Vanilla columns are machine-owned.**
  - Never edit them by hand. Re-run `python3 tools/extract_vanilla_jokers.py` instead.
  - The extractor re-merges design columns by `vanilla_key`, so re-running never loses design work.
- **`vanilla_effect`:**
  - Formatting codes are stripped, lines are joined with spaces, and `#n#` placeholders are replaced by their values at card creation.
  - Values that depend on run state (e.g. "Currently ...") show the default the game shows outside a run.
  - Values that can't be computed outside a run (e.g. The Idol's card) are written as `<?>`.
  - `vanilla_loc_vars` lists every placeholder's Lua expression, its value, and its kind (`static` / `runtime` / `unresolved`).
  - The untouched localization text is in `vanilla_effect_raw`.
  - `plannig/design/vanilla_extract_report.md` lists every joker with a runtime or unresolved value.
- **Status flow:** `draft → approved → implemented → tested`. Only the human sets `approved`.

## 9. Testing acceptance tests

Acceptance tests are automated and run inside the real game with `./dev.sh test` (full guide and API: `docs/testing.md`). Every acceptance test in the CSV row must become a test, and a ticket is only `tested` when they all pass.

1. **Test file.** Each ticket gets `mod/dev/tests/jokers/<vanilla_key>.lua`, with one `T.test` per acceptance test. Name each test after the row's test text, e.g. `'Ride the Bus+: 3 hands without face cards -> +3 Mult'`.
   - **Setup:** `T.start_run{ jokers = {...}, ... }` takes the same fields as a scenario. It is seeded (`BPTEST`) by default, so tests are deterministic.
   - **Exact hands:** `T.set_hand{'KS', 'KH', ...}` makes the hand exactly those cards.
   - **Actions:** use only `T.*` actions (`T.play`, `T.discard`, `T.buy`, `T.use`, ...). Never call `G.FUNCS.*` directly.
   - **Expected values:** write them as arithmetic that explains itself: `T.eq(r.mult, 2 + 4 + 4)`.
   - **Vanilla comparison:** where the "+" joker modifies a vanilla number, assert the vanilla value too (see `mod/dev/tests/vanilla/`).
2. **Run.** Use `./dev.sh test <vanilla_key>` while working and `./dev.sh test` before committing.
   - The command restarts the game itself when mod code changed.
   - Tests run on a separate test profile (profile 3), never the player's.
   - Exit code 0 means everything passed.
3. **Upgrade path.** Once `BPlus.upgrade_card` exists, every joker with non-empty `state_transfer` also gets an upgrade test:
   - give the vanilla joker
   - build up its state through real play (`T.play`, `T.to_shop`, ...)
   - call `BPlus.upgrade_card(T.joker('<vanilla_key>'))`
   - assert the transferred values, the edition and the stickers (set them with scenario fields such as `{ key = ..., edition = 'foil', stickers = { 'eternal' } }`)
4. **Before marking `tested`:** `./dev.sh check` must be clean and `./dev.sh test` must pass with no failures or errors.
5. **Record results.** Paste the `PASS` lines for the ticket's tests into the commit message.
6. **Manual poking (optional).** For exploring by hand there are `mod/dev/scenarios/<name>.lua` + `./dev.sh scenario <name>`, `./dev.sh eval '<lua>'` and DebugPlus. These are aids, not acceptance tests.

## 10. Commits

- **One ticket = one joker = one commit:** the joker file and the test file. Commit only your own paths
  (`tools/commit.sh "<message>" <files...>`, which serialises commits between parallel agents). CSV statuses are
  updated by the orchestrator in batches.
- **Message format:** `joker: <vanilla_key> -> <plus_key>`, followed by the acceptance test results.

## 11. JokerDisplay (D18, D20)

Every "+" joker (and Carpenter / Apprentice) declares `joker_display_def` inside its `BPlus.Joker{}` call.
It mirrors the vanilla definition in `Mods/JokerDisplay/definitions/display_definitions.lua` for the same joker,
adapted to the "+" `config.extra` field names (`ref_table = 'card.ability.extra'`, not `'card.ability'`).
Vanilla jokers with an empty definition (`{}`) get `return {}`.

```lua
joker_display_def = function(JokerDisplay)
    return {
        text = {
            { text = '+' },
            { ref_table = 'card.ability.extra', ref_value = 'mult', retrigger_type = 'mult' },
        },
        text_config = { colour = G.C.MULT },
        -- reminder_text = {...}, extra = {{...}}, calc_function = function(card) ... end
    }
end,
```

- Behaviour switching is handled centrally (`behavior.lua`): JokerDisplay's init/calculate/update run under the
  behaviour swap, and the display rebuilds when the behaviour changes. A vanilla joker next to Carpenter
  uses the "+" definition and vice versa, so write the definition only against the "+" shape.
- Numbers in `ref_value`s come from `card.ability.extra.*` (live), or from `calc_function` writing to
  `card.joker_display_values.*` (derived values). Never hard-code numbers.
- Use `calc_function` and `card.joker_display_values` for anything that needs a computation; text nodes can only
  read a field by name.
- Tests: `T.joker_display(k).text` (docs/testing.md "Testing JokerDisplay"): the "+" joker, vanilla forced to
  `'plus'`, "+" forced to `'base'`.
